## Provenance (why you can trust this list)

Produced by a multi-agent deep audit: 9 dimension audits (first-run, inbox loop, dashboard, status page, design system, navigation, microcopy, accessibility, trust cues) + 2 method-acted persona walkthroughs + 2 comparable-SaaS research sweeps (Gorgias, Front, Zendesk, Intercom, Plain, Linear, Superhuman, Stripe, Vercel, Notion, Loom). 114 raw findings → 86 after dedup → **every one adversarially re-verified against the code** → 85 confirmed, 1 refuted. Every task below carries real `file:line` evidence that a verifier independently re-opened.

Companion data (same directory):
- `ux-audit-findings-2026-07-06.json` — all 85 findings with full problem text, evidence, and verifier notes. Task ids below (UX-01…UX-85) are the array order in that file.
- `ux-audit-research-2026-07-06.json` — the 23 comparable-SaaS patterns.

## The bar every change is judged against

Two adoption personas. Every task exists because it failed one of them:

- **Persona A — the day-one junior rep.** The pitch: a founder can delegate escalation-grade presale issues (chargeback threats, hostile refunds, VIP anxiety) DOWN to a tier-1 rep with confidence, because Tideover encodes the senior playbook. So the rep must always know: *what do I do first, is this draft safe to send, what happens if I click this, where do I go when confused.* Fear of breaking things is the #1 adoption killer.
- **Persona B — the solo founder at 11pm, 15 minutes a day.** Needs: glanceable "am I okay?", the next action one click away, zero ceremony, zero seconds wasted.

North star: **stupid simple**. If a screen needs explaining, it's a defect.

## Design direction — LOCKED (apply consistently, don't re-litigate per task)

These are the product-level calls. Individual tasks below implement them.

- **D1 · One action color.** Terracotta (`--terracotta`) means exactly one thing: *clickable primary action*. It currently also serves as the caution color (`--risk-amber` is byte-identical, `globals.css:18` vs `:30`) and as decorative tag fill. Create a distinct caution token `--amber-status` (a warm yellow-gold, clearly not terracotta's hue — e.g. around `#C99A2E`, verify contrast) and repoint `.pill-amber`, SlaChip's amber tone, and every RiskColor `amber` use to it. Terracotta appears **only** on things you can click.
- **D2 · Fixed status vocabulary (Vercel-style).** Green = good/safe (and *only* when something is actually good — never as a default), amber-status = watch, risk-red = act now. Color never carries meaning alone: every colored state pill also has a text label or title. Reserve animation/pulse for genuinely in-flight states.
- **D3 · Pill shape = live state signal, nothing else.** Pills/badges are reserved for the ≤3 things a rep must react to (risk, SLA, escalated/overdue). Static descriptors ("Draft only · human-approved", "Normal priority") demote to plain caption text.
- **D4 · Land on the work.** The operator's home is the Inbox, not the finance dashboard. The dashboard's first element is the day's action, not analytics. The word "cockpit" is internal jargon — the UI says **Inbox**.
- **D5 · Plain words, glossed jargon.** WISMO, LTV, deflection, SLA, de-escalate, confidence band: every occurrence gets either plain language or an in-place gloss (`title=` at minimum). New microcopy follows the anti-slop standard (`gtm-assets/copy-standard.md`): tight, concrete, no filler, never the word "honest".
- **D6 · Accessibility floors.** `--ink-mute` darkened to clear WCAG AA 4.5:1 on both `--sand` and `--paper`; focus outlines never suppressed; disabled ≠ enabled visually; color-meaning always paired with text; icon-only controls get aria-labels.
- **Keep** the warm sand/teal brand feel, the Fraunces/Inter pairing, and the calm tone. This is a hierarchy-and-guidance overhaul, not a rebrand.

# WAVE 1 — do these first (full spec)

### UX-01 · [HOT] Regenerate never updates the visible draft — rep can re-send stale text believing it's new
- **Severity/effort:** P1 / S · **Sources:** 4 independent auditors · **Files:** `components/product/DraftRail.tsx`, `components/product/ApprovalBar.tsx`, `app/app/inbox/page.tsx`, (read) `app/api/draft/route.ts`
- **Problem:** Clicking Regenerate flashes "Regenerating…" then shows the OLD draft. The textarea seeds once from `useState` (`DraftRail.tsx:56`) and DraftRail is keyed only on `ticket.id` (`inbox/page.tsx:255`), so `regenerate()` (`ApprovalBar.tsx:85-96`) posts, gets a fresh draft back, discards it, and `router.refresh()` re-renders a component whose local state never re-syncs.
- **Change:** Thread the regenerate result into the editor. Either (a) add an `onRegenerated(newText)` callback wired from ApprovalBar → parent → DraftRail that calls `setText(data.draft.text)` and resets mode to standard, or (b) include a regen nonce in DraftRail's `key` so it remounts with the new seed. Guard: if the rep has unsaved edits (text ≠ seed), ask before clobbering. Show a brief "New draft ready" cue (reuse the pill/caption pattern).
- **Done when:** clicking Regenerate visibly replaces the textarea content with the newly returned draft; unsaved manual edits prompt before being replaced; j/k → Enter → ⌘Enter flow still works.

### UX-02 · Escalated/hostile queue flag is an invisible 6px dot
- **Severity/effort:** P1 / S · **Sources:** 2 · **Files:** `components/product/QueueList.tsx`
- **Problem:** The most important triage signal — hostile / chargeback-threat — renders as a bare unlabeled 6px dot (`QueueList.tsx:72-77`), independent of the risk pill, so a rep scanning by color walks right past a chargeback threat that shows a calm green/amber risk score.
- **Change:** Replace the dot with a small visible text pill (`pill pill-red`, label "Escalated") rendered beside the risk badge on the row. Keep aria-label.
- **Done when:** an escalated ticket is identifiable in the queue list at a glance, by label not just color (D2).

### UX-03 · [HOT] No confirmation a send worked before the view jumps to the next ticket
- **Severity/effort:** P1 / S · **Sources:** 2 · **Files:** `components/product/ApprovalBar.tsx`
- **Problem:** On success the UI instantly `router.replace()`s to a different customer (`ApprovalBar.tsx:108-131`) — no "Reply sent", no aria-live. A day-one rep who just replied to a hostile customer can't tell it worked; may re-click or ask a human. (The "Reply sent." card at `:152-163` only renders for already-sent tickets.)
- **Change:** Before `advance()`, render the existing "Reply sent." confirmation briefly (~500ms or until next keypress), wrapped in `role="status" aria-live="polite"`. Add "Sent by {approvedBy}" to the post-send card while in the file (pairs with UX-49).
- **Done when:** every successful send produces a perceivable confirmation (sighted + screen reader) before auto-advance; the send loop still feels fast.

### UX-04 · Sidebar "Demo data" label is hardcoded — real merchants see live data labeled demo
- **Severity/effort:** P1 / S · **Sources:** 1 · **Files:** `components/product/Sidebar.tsx`, `app/app/layout.tsx`
- **Problem:** `Sidebar.tsx:116-118` always renders literal "Demo data" under the operator name. A real pilot (DEMO_MODE=false) sees live customer data falsely labeled demo on every screen — contradicts the proof-only promise. (Contrast the correctly gated `{isDemoMode() && <DemoBadge/>}` at `app/app/layout.tsx:23`.)
- **Change:** Pass `isDemo={isDemoMode()}` from AppLayout into Sidebar; wrap the label in `{isDemo && …}`.
- **Done when:** the label appears in demo mode only.

### UX-05 · One-click "Send gift" spends company money with no confirmation
- **Severity/effort:** P1 / S · **Sources:** 1 · **Files:** `components/product/GiftSuggestion.tsx`
- **Problem:** The Send gift button (`GiftSuggestion.tsx:101`) logs an irreversible comp on the first click (`:51-72`) with dollar figures attached and no confirm, no authorization cue. Persona A either freezes ("am I allowed to spend money?") or mis-spends.
- **Change:** Two-step inline confirm ("Send this gift? **Confirm** / Cancel") plus one caption line: the value comes from the merchant's goodwill budget and the rep is authorized. No modal.
- **Done when:** a gift cannot be sent with a single click; the authorization line renders; copy passes anti-slop.

### UX-06 · [HOT] Confidence chip is hardcoded green even on overdue/escalated tickets
- **Severity/effort:** P1 / S · **Sources:** 1 · **Files:** `components/product/DraftRail.tsx`
- **Problem:** `DraftRail.tsx:97` renders the confidence-band chip as `pill pill-green` unconditionally — directly beside a red "Overdue" pill on the same ticket (`:104-106`). Green = safe everywhere else; this is a conflicting signal exactly where persona A asks "is this safe?"
- **Change:** Make the confidence-band chip a neutral informational chip (border-border, bg-sand, text-ink-mute — match SlaChip's "ok" tone). Per D2, green appears only when nothing is wrong.
- **Done when:** no green renders on a ticket that is overdue or escalated.

### UX-07 · [HOT] Operator lands on a finance dashboard, not the queue; the only path is a jargon link
- **Severity/effort:** P1 / M · **Sources:** 1 · **Files:** `app/login/page.tsx`, `app/app/page.tsx`
- **Problem:** Login's `next` defaults to `/app` (`login/page.tsx:16`) — a wall of finance metrics titled "Refund-risk dashboard" with no ticket to answer; the only route to work is a small "Open cockpit" text link (`page.tsx:228`), and "cockpit" means nothing to a day-one rep.
- **Change:** (a) Default post-login destination → `/app/inbox`. (b) On the dashboard, add a full-width primary action as the FIRST element under the header: "Answer your queue ({N} waiting) →" when N>0, calm "All caught up" when 0 (this is also UX-17's banner — build once). (c) Replace every rep-facing "cockpit" with "Inbox" (grep `app/`, `components/product/` for the word).
- **Done when:** a fresh login lands in the Inbox; the dashboard's first element is the queue CTA; "cockpit" no longer appears in rep-facing UI.

### UX-08 · [HOT] Dashboard at-risk count + table never clear as you work
- **Severity/effort:** P1 / M · **Sources:** 1 · **Files:** `lib/service.ts`, `app/app/page.tsx`
- **Problem:** `getDashboard`'s `atRisk` filter (`service.ts:734`) never excludes sent tickets, unlike the inbox's `openQueue` (`inbox/page.tsx:68`). After clearing the queue, the dashboard still shouts "5 flagged at-risk" with rows linking into handled tickets — the operator can't trust the number and re-opens finished work.
- **Change:** Exclude `status === "sent"` from the at-risk work-count and table so the dashboard drops toward 0 as the queue clears (or render a "Replied" chip on sent rows and count only open — pick the first; it matches the inbox's definition of work).
- **Done when:** clearing the inbox brings the dashboard's flagged count to 0 without a reseed; no test/golden drift (this is presentation-layer counting, but re-run the full gate).

### UX-09 · [HOT] No live "is anything on fire" signal on the dashboard
- **Severity/effort:** P1 / M · **Sources:** 1 · **Files:** `app/app/page.tsx`, (reuse) `lib/sla.ts`
- **Problem:** The screen meant to answer "am I okay right now?" shows only a lagging "SLA attainment 96%" (`page.tsx:100-109`). Live per-ticket breach state already exists (`ticketSlaState`, used at `inbox/page.tsx:82`) but is never aggregated here — "3 replies are overdue" is unknowable at a glance.
- **Change:** Compact status strip under the H1: "{N} waiting · {X} overdue · {Y} due soon", each figure linking to the inbox. Derive by running `ticketSlaState` over open tickets — counts of real state only, no fabricated metric. Color per D2 (red only when overdue > 0).
- **Done when:** dashboard shows live overdue/due-soon counts that match what the inbox SlaChips show, one click from the fix.

### UX-10 · [HOT] "Escalate" is cosmetic — nothing persists, no one is notified *(promoted from P2 by Fable: 6 independent reports; the delegate-with-confidence pitch depends on this being real)*
- **Severity/effort:** P1 / M · **Sources:** 6 · **Files:** `components/product/ApprovalBar.tsx`, new `app/api/escalate/route.ts` (+ thin lib), `app/app/inbox/page.tsx`, `app/app/page.tsx`
- **Problem:** The rep clicks Escalate on a chargeback threat, sees "Flagged for manager review," moves on trusting a human will catch it — but the flag is local React state (`ApprovalBar.tsx:45`, `:233-239`) that vanishes on advance/refresh. No API route or persisted field exists. The safety valve the whole junior-rep pitch depends on is copy theater.
- **Change:** Persist it. POST `/api/escalate` writes an `escalated-by:<operator>` tag + timestamp on the ticket (reuse the gift-sent tag pattern; repository seam, both drivers). Surface flagged tickets: a "Flagged" pill in the queue row and a count on the dashboard status strip (UX-09). Include a structured handoff note in the flag payload: the current draft + a short "why" the rep types (one optional text field) — per the Front escalation-handoff pattern (R11). Testable-core rule: logic in `lib/`, route stays thin. Add a unit test.
- **Done when:** an escalation survives refresh/navigation, is visible in queue + dashboard, and records who/when/why; the button copy matches reality.
